# Database map

This document explains the SQLAlchemy schema by ownership area, primary writers/readers, and invariants. It owns table-level navigation and persistence concepts; it does not define migrations or runtime algorithms.

Method-level repository split planning lives in `docs/architecture/database-method-inventory.md`. That inventory maps every public `Database` method to its target repository owner, primary call-site areas, relevant tests, and extraction risks.

`user_actor_outbound_deliveries.direct_authorizations_json` stores optional bounded direct-recipient authorization evidence independently from follower relations. All four canonical local/remote post/comment tables contain durable mutation revision, content and tombstone fields; all four physical copy tables contain revision and mutation-attempt state. The v0→v1 upgrade leaves unknown historical content and confirmations NULL instead of inventing them.

`activitypub_event_receipts` keeps lifecycle `status` separate from semantic `outcome`; legacy rows may have `NULL` outcome. `activitypub_event_receipts`, `message_mappings`, `published_activity_objects`, `remote_actors`, Discord snapshot tables, and the community group tables are shared infrastructure for deduplication, object lookup, dashboard labeling, and fanout. `management_audit_events` is separate backend management observability state, not ActivityPub receipt or fanout infrastructure.

Guild-id columns on remote subscriptions, local communities, and local subscribers may be nullable for legacy or incomplete rows, but such rows are not routable: Discord fanout validates a positive integer guild id and skips malformed targets before Discord, mapping, dedup, or retry side effects.

Channel exclusivity is enforced by `platform_channel_surfaces`: four typed owner FKs are the source of truth, a CHECK admits at most one owner, and `role` is generated and stored. Claim/release operations use the caller's transaction; failed/inactive domain rows retain occupancy until explicit release. Local community actors contain no physical Discord host columns.

Content copies retain connector/channel pairs, external thread/message/parent IDs, and scoped uniqueness. Composite FKs reject mismatched connector/channel pairs; message surfaces also reference their parent thread's channel. Source rows permit unknown locations while retaining a known connector. Release, deletion of a claim, and rebinding preserve historical copies. Nullable legacy Discord columns are temporary compatibility projections; current Discord routing requires a matching `discord-primary` typed claim and valid protocol kind. ActivityPub actors, canonical IDs, and shared Follow/Undo state remain global.

## Bridge actor signing identity

`bridge_actor_keys` stores the single bridge service actor keypair. Registered-user keys remain on `users`, and local-community keys remain on `local_communities`; backups of the SQLite database therefore preserve all local actor identities together.

## User profile foundation

`users` now owns nullable `display_name`, `summary`, `avatar_media_id`, and `header_media_id`. `user_profile_fields` stores up to four ordered metadata rows. `profile_media_assets` stores immutable media metadata; bytes live under the durable profile-media root. SQLite foreign keys use `ON DELETE RESTRICT`, and triggers enforce that avatar/header slots reference matching media kinds.

`users.profile_version` has both application default 0 and SQL server default 0, identical for fresh and migrated schemas. Supported persisted schema identity is current v1; direct released-v0 transfer uses the pinned `src/db/legacy_v0.sql` source and this ORM target, without an intermediate business schema. Recognition and transaction details are described in [SQLite startup migrations](../development/database-migrations.md).
