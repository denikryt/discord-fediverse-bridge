# 145 — Fluxer-only runtime and verified transport (#12 / area 05)

**Base:** `feature/fluxer-support` at `2fd0fdd2`, based on `feature/platform-independent-bridge` at `1645689c`. **Target:** finish area 05, not implement areas 06–10. **Status:** revised after architecture reviews F1–F6; implementation plan only. Live Fluxer acceptance and current-`main` integration are not established.

## Problem / Goal

[Issue #2, decision 6898714764](https://github.com/denikryt/discord-fediverse-bridge/issues/2#issuecomment-6898714764) replaces the simultaneous Discord+Fluxer process with **one platform per Bridge Service instance**. [Issue #12, decision 6898803249](https://github.com/denikryt/discord-fediverse-bridge/issues/12#issuecomment-6898803249) requires Fluxer-only startup without Discord credentials or SDK initialization, while preserving Discord-only startup and finishing real REST/Gateway acceptance.

The branch already has a Fluxer SDK sidecar, typed adapter, authenticated private ingress/RPC, persistent create claims, connector-specific recovery and Docker Compose packaging. It is **not** a standalone Fluxer runtime: `Settings.discord_token` and Discord super-admins are mandatory; `app.main()` always starts `BridgeBot`; `build_runtime()` always constructs and binds Discord owners; `Runtime.close()` assumes those owners exist. Production `fluxer-connector/src/main.ts` exposes reads but rejects all writes; `capabilities.ts` reports writes unsupported; `permissions.ts` leaves action-specific writes unproven. Current live documentation reports earlier self-hosted REST receipt defects that were fixed in code but not re-accepted on the corrected build.

**Goal:** make `discord` and `fluxer` mutually exclusive runtime configurations, retain the current common core/SQLite/Fedify infrastructure, finish Fluxer forum/thread/message **transport**, and prove it through real-instance checks before declaring #12 complete. ActivityPub community publication/subscription, Fluxer user registration and dashboard management are **not** part of #12.

## Expected Behavior

A Discord instance behaves as before. A separate Fluxer instance starts Python HTTP/Fedify/SQLite plus one authenticated Node SDK sidecar, without creating a Discord client or using Discord credentials. Fluxer forum/message REST reads and verified writes work behind the existing `PlatformAdapterPort` and persistent delivery controls. Fluxer Gateway events enter the authenticated Python sink but cannot yet publish canonical ActivityPub content. The two modes never share one active platform registry, bridge database, or public actor identity.

## Specification

1. **S01 — Selection.** `BRIDGE_PLATFORM` accepts exactly `discord` or `fluxer`; absence defaults to `discord` for existing deployments. Any other value fails during settings validation, before DB/SDK/network side effects. A process exposes exactly one active `ConnectorRef` and adapter; there is no combined mode.
2. **S02 — Discord configuration.** Discord mode requires nonempty `DISCORD_TOKEN` and the existing nonempty `BRIDGE_SUPER_ADMIN_USER_IDS`. It rejects nonempty `FLUXER_CONNECTORS_JSON`; it does not instantiate or expose Fluxer RPC/ingress. Existing Discord OAuth and Personal Feed services stay enabled.
3. **S03 — Fluxer configuration.** Fluxer mode requires exactly one valid `FLUXER_CONNECTORS_JSON` entry (same approved origin/key/loopback RPC/bearer contract as now). It does not require `DISCORD_TOKEN`, Discord OAuth settings or Discord super-admin IDs; supplied Discord bot/OAuth credentials are rejected as mixed configuration. No `BridgeBot`, `DiscordAdapter`, Discord OAuth client or Discord-specific workers are constructed, started or closed.
4. **S04 — Persistent ownership and pre-migration refusal.** After acquiring the existing runtime/deployment locks and recovering an incomplete restore, inspect persisted SQLite mode **read-only before `database.migrate()`**. Discord mode refuses an existing Fluxer binding; Fluxer mode refuses every initialized released-v0 Discord DB, a v1 DB with Discord-authored channel/community/subscription/copy/registration/user state, multiple or mismatched Fluxer bindings, and a v1 DB containing a `bridge_actor_keys` record **without the exact persisted Fluxer connector binding**. A new/empty DB and v1 DB containing only the inert bootstrap `discord-primary` metadata row with no keys or platform-owned state are eligible for first Fluxer admission. On success, transactionally admit exactly one `(connector_key, platform='fluxer', instance_origin)` **before** creating the bridge actor key; subsequent Fluxer restarts require the same binding. An unknown or partial database shape fails closed. Any rejected startup leaves existing schema version, persisted data, actor URLs and signing keys unchanged; never silently migrate, rebind or split an incompatible DB.
5. **S05 — Lifecycle.** Fluxer-only `app.main()` runs HTTP and the common workers without a Discord Gateway task. The Python process remains healthy while the optional Node sidecar is temporarily offline; physical Fluxer dispatch is unavailable and pending rows remain pending. SIGTERM or service failure stops admission, joins in-flight ingress/writes/workers, then closes RPC/Fedify/SQLite and releases lifetime/deployment locks in that order. Discord mode retains its existing Gateway lifetime supervision.
6. **S06 — Private interface.** Fluxer SDK and token remain Node-owned; Python holds only the separate private bearer. RPC binds loopback, is not published, and uses exact connector identity and bearer; Python ingress independently authenticates every event. Invalid/missing bearer, wrong connector/origin, malformed DTO, shutdown-time request, and unexpected redirects fail closed. Do not introduce another direct HTTP SDK client in Python.
7. **S07 — Discovery/readiness and write admission.** The sidecar uses `/.well-known/fluxer` and the explicitly approved API/Gateway hosts. Python requires READY, exact connector key/origin/verified bot ID and no Gateway gap before physical dispatch. **Independently, `FluxerNodeService` rejects every effectful RPC when `session.health().gateway_gap`, `gatewayFault`, or an SDK bot identity mismatch is present, immediately before calling the executor and without an intervening await**; a Python attestation made earlier is insufficient. Live SDK identity must have `currentClient.user.bot === true` and a nonempty `currentClient.user.id` exactly equal to the `bot_id` attested at login (`session.health().bot_id`). While that identity differs, authenticated Node `health` reports `state=degraded` rather than `ready`, even if the cached SDK session reports READY; Compose and Python must therefore refuse transport readiness. The guard covers `create_forum_thread`, `create_reply_thread`, `send_message`, `edit_message` and `delete_message`; read-only RPC may remain available during a gap or identity mismatch. Reconnect/disconnect/replaced bot identity revokes writes. A `shardReady` alone does not clear a latched gap; resume only after the existing SDK recovery protocol has verifiably cleared it (otherwise restart the sidecar). Already-admitted in-flight writes retain S13 uncertainty handling if the link changes during an SDK await. Public `/healthz` indicates Python health, not Fluxer transport readiness.
8. **S08 — Physical reads.** `fetch_channel`, `fetch_thread`, `fetch_message`, `check_permissions`, and `capabilities` use fresh, connector/guild/container-scoped evidence. A full REST Message without `guild_id` is accepted only when a separate fresh container read establishes its exact guild; an explicit contradictory guild, container, author or webhook provenance is rejected.
9. **S09 — Forum creation.** For a verified forum in an authorized guild, a bot-mode `create_forum_thread` creates one public forum post with its starter message and returns **independently verified** `(forum_id, guild_id, thread_id, starter_id)`. Equal and different thread/starter IDs are valid. A missing/mismatched starter, unknown tag requirements, unavailable/restricted required tag, unsupported content, foreign guild, or unverifiable permission prevents admission or leaves post-write status uncertain; no inferred starter ID.
10. **S10 — Messages/replies.** `send_message` targets the verified immediate thread/channel; `reply_to` must reference a real message in the **same** container. Nested replies preserve the immediate parent. Thread sends check `SEND_MESSAGES_IN_THREADS` separately from forum `SEND_MESSAGES`. Bot-owned echo events do not become new source publications. `create_reply_thread` from a text message remains explicitly unsupported in #12 (not used by forum flows).
11. **S11 — Mutations.** Edit/delete operate on an exact existing bot-owned message after fresh SDK read, container/guild/author/`webhookId === null` checks and action-specific eligibility. A wrong author, webhook, missing message, revoked permission or unsupported payload refuses the operation. A reply/message delete never silently deletes its parent thread.
12. **S12 — Capabilities/ACL.** The production capability response reports only operations whose SDK method, channel type, current permissions and measured server contract have been verified. Resolve the current permanent `unknown` responses for forum create, thread send and bot-owned edit/delete using the official permission contract and fresh SDK state; do **not** turn every unknown into allowed. Webhook display identity, attachments and other unsupported operations remain false. `unsupported`/`denied` never trigger an unverified fallback write.
13. **S13 — Transport uncertainty and durable delivery.** A direct `FluxerAdapter.edit_message()` / `delete_message()` call issues at most one effectful RPC per invocation and reports a lost or unverifiable response as `unknown_delivery`; the adapter does **not** persist a mutation claim or prevent a caller from explicitly invoking it again after restart. Only existing SQLite-owned `CreateAttempt`/dispatch proof and `PlatformPhysicalMutationCoordinator` claims/acknowledgements provide cross-attempt and cross-restart retry authority for their respective coordinator-managed operations: no second write after an uncertain effect without positive attempt-correlated reconciliation proof. Unverified coordinator-managed effects remain unresolved for operator handling, not matched by title/body guesses. The Fluxer canonical mutation coordinator is not connected to the running Fluxer-only mode until #13 (S15).
14. **S14 — Gateway ingress.** Actual SDK Gateway create/update/delete and thread create/update/delete events normalize to existing DTOs, preserve exact connector and verified forum ownership and survive reconnect/resume, late/out-of-order and missing-context cases. Unknown forum, bot/webhook echo and wrong connector do not produce canonical publication or surface mappings. Accepted callbacks are joined on shutdown.
15. **S15 — Federation stage boundary.** Fluxer-only exposes the common Fedify transport and stable bridge origin/keys, but Fluxer Gateway observations do **not** create AP objects, register users, host communities or accept remote subscriptions in #12. The Fluxer-only recovery lane does **not** schedule canonical physical mutation delivery or invoke the Discord-only canonical renderer; this returns in #13 after real Fluxer community ownership exists. No synthetic Discord ownership is created to satisfy existing code. Fluxer author/registration support is #14; Fluxer↔ActivityPub communities/subscriptions are #13.
16. **S16 — Public HTTP boundaries.** `/healthz`, core Fedify routes and public dashboard shell remain usable without a Discord bot. Discord OAuth registration routes are absent in Fluxer mode; `/register` and related registration writes respond with a clear non-successful unavailable result until #14, without issuing a Discord OAuth redirect or creating an unverified user. Do not enable privileged Discord-origin management calls in Fluxer mode; active-platform dashboard operations arrive in #15.
17. **S17 — Deployment.** Default Compose and environment remain Discord-only. The `fluxer` profile deploys Python+Node+Fedify for `BRIDGE_PLATFORM=fluxer`, with sidecar `network_mode: service:bridge`, Node-only bot secret mount, loopback RPC and truthful readiness checks. Two independent instances use separate Compose project/volume names, public domains, AP keys, database paths, bot credentials and published ports; they do not join an internal community by construction.
18. **S18 — Regressions.** Both modes preserve current typed AP identity scheme, connector-scoped physical IDs and persisted links; Discord-only preserves existing OAuth, User Actor, Personal Feed, forum subscriptions, Local Community post/reply/edit/delete and recoverable fan-out. Valid Discord v0→v1 migration remains repeat-safe in Discord mode; failed Fluxer admission on an old Discord v0/v1 dataset makes **no migration or key change** (S04). Existing Discord-only mutation routing and rendering remain byte-for-byte stable.
19. **S19 — Acceptance.** #12 is complete only after the corrected production Node dispatcher, full Python/Node suites, two real deployment modes, actual authenticated Gateway and forum REST writes/readbacks, permission-denial cases, restart/recovery and secret/namespace isolation are tested on a recorded Fluxer server build. Deterministic SDK fakes and static Compose YAML are necessary regressions but are **not** sufficient acceptance evidence.

## Architecture

**Review scope correction:** F1/F2 fix early DB/identity ownership; F3 fixes the SDK-owning Node write-admission boundary; F4 defers unreachable Fluxer federation mutations to #13. No part of #12 creates an operational Fluxer community or canonical remote mutation target; the Fluxer-only mutation worker is not registered rather than relying on a Discord renderer or an artificial target-policy branch.

### A1. Active platform at the composition root

- Add `bridge_platform: Literal['discord','fluxer']` to `Settings`, default `discord`; make Discord settings optional at the field level and enforce them in a cross-field model validator for Discord mode. Fluxer mode validates exactly one existing trusted connector and absence of Discord credentials. Preserve the strict `parse_fluxer_connectors()` schema rather than adding another secret source.
- `app.build_runtime()` opens the **common** owners once: DB/migration and leases, actor keys, Fedify client, content publishing, common policy, canonical fan-out, physical coordinator/scheduler and necessary background workers. Compose **only** the selected platform owners: Discord `BridgeBot`/adapter/event router/OAuth/Personal Feed physical worker **or** Fluxer RPC/adapter/observation sink. The adapter registry and capacity/scheduler keys contain exactly the active connector; no default Discord fallback. The existing fan-out recovery scheduler remains active in both modes, but its **canonical mutation coordinator is present only in Discord mode** until #13; keep the scheduler mutation drainer optional rather than creating a Fluxer mutation formatter with no source ownership.
- `Runtime` holds explicit optional Discord and Fluxer owner groups or optional typed fields (choose the smaller change after existing call-site tests), including optional `physical_mutation_coordinator` in Fluxer-only mode; `close()` and `_validate_runtime_graph()` check the active graph, join only constructed owners and keep existing failure quarantine/lease semantics. `main()` supervises HTTP plus Discord Gateway only in Discord mode; in Fluxer mode the sidecar is a separate Compose service, not a Python TaskGroup task. Do not introduce a new task supervisor, relay, database or SDK abstraction.
- Any common runtime service currently depending on `BridgeBot`/Discord notices is split into its generic persistence/federation part and **mode-specific binding** only where called. In #12, community source and registration operations remain unavailable in Fluxer mode (S15–S16), so do not fabricate no-op Discord clients. Check indirect call paths: AP Follow notices (`activitypub_handlers._notify_channel_accepted`, `UserActorFollowService`), user-message reconciliation (`UserActorDeliveryService`), registration routes and dashboard reads. Reject user-targeted Follow/Undo as unknown in Fluxer mode before accessing Discord notifier; do not claim they were accepted or persisted.

**Owner / identity / lifecycle:** `Settings.bridge_platform` is process-immutable; `PlatformAdapterRegistry` owns exact *active connector selection*, not SDKs or DB rows. `Runtime` owns Python callbacks, leases, scheduler and Fedify; Discord SDK (if selected) belongs to the Discord bot context; Fluxer SDK/bot token belong exclusively to the Node sidecar. `PlatformConnector` rows remain SQLite-owned, key+origin immutable. Each persisted content object keeps its canonical AP identity independently of physical copies. Key invariant: `len(active_adapters) == len(dispatch_connector_keys) == 1` and every physical reference resolves to that connector.

### A2. Enforce instance separation using existing persistence

- Add an exact read-only `preflight_instance_mode` boundary alongside `PlatformSurfaceRepository` in `src/db/repositories/platform_surfaces.py`, called from `src/app.py:_build_live_runtime` **after** `acquire_runtime_lifetime_lease`, `recover_incomplete_restore` and acquisition of the deployment shared lease, **before** `Database(...)`, `ProfileMediaStore.initialize()`, `database.migrate()` and key bootstrap. Read the configured SQLite file using a `mode=ro` URI (no writer connection or create-on-open). Distinguish a nonexistent/empty file from an initialized released-v0 DB using `sqlite_master` + `PRAGMA user_version`; refuse a released-v0 schema for Fluxer regardless of row counts. Reject an unknown/partial schema rather than treating it as empty. On current v1 read exact `platform_connectors`, `bridge_actor_keys` existence and Discord-provenance tables (including `platform_channel_surfaces` joined to `discord-primary`, `users`, `registration_sessions`, community/subscription/personal-feed and physical mapping rows). Treat `discord-primary` **alone** as inert but a persisted service actor signing key without the **same configured Fluxer binding** as a previous identity owner. Do not log private key material.
- A saved Fluxer connector matching `(connector_key, instance_origin)` allows the same Fluxer instance to restart; a mismatch or second Fluxer connector refuses the mode. Any saved Fluxer binding refuses Discord mode **before** migration. After preflight, retain normal `database.migrate()` and `PlatformSurfaceRepository.admit_single_trusted_fluxer()` under its existing transaction, then `BridgeActorKeyBootstrap.ensure()`: preflight is conservative early refusal, **not** a substitute for final schema/identity/admission checks. Do not infer a past platform from `discord-primary` alone; do not silently import a signing key from an unbound v1 file.
- Do not add a bridge-instance table, change DB version, rewrite released-v0 migration or create a new migration runner. Keep `PUBLIC_BASE_URL`/Fedify identity requirements; distinct domains/databases are deployment configuration. Source precedents: project `src/db/migrations.py` explicitly commits v0→v1 with `PRAGMA user_version`; [SQLite URI `mode=ro`](https://www.sqlite.org/uri.html) and [Python sqlite3 URI](https://docs.python.org/3/library/sqlite3.html#how-to-work-with-sqlite-uris) permit a non-creating read-only inspection.

### A3. Complete the already-built Fluxer write path

- Keep `src/fluxer_adapter.py` as the only Python physical interface; keep SQLite admission/claim/receipt in `content_sync/platform_fanout.py`, `platform_mutations.py` and scheduler. In Node `main.ts`, register **existing** `createSdkForumCreateHandler`, `createSdkMessageSendHandler` and `createSdkMessageMutationHandler` only after their verified production acceptance; no duplicate raw REST sender or new queue.
- Keep `src/app.py:physical_mutation_policy` and `physical_mutation_content` **Discord-only** for this stage; instantiate and pass the canonical mutation coordinator to the scheduler **only in Discord mode**. In Fluxer mode pass `mutations=None`, skip only mutation scans, and retain fan-out/recovery lanes. Do not activate Fluxer canonical Update/Delete routing or invent a Fluxer formatter before #13 creates verified Fluxer community/subscription/copy ownership. In #12, verify `edit_message` / `delete_message` as direct bot-owned **transport** operations through the existing Python adapter → authenticated Node RPC → actual SDK executors (S11), with negative ACL/provenance and direct-call `unknown_delivery` reporting (S13), **not** persisted mutation idempotency. Exercise existing generic `PlatformPhysicalMutationCoordinator` claims and CreateAttempt records as separate SQLite regressions, not as proof of a currently reachable Fluxer federation workflow. In #13, connect the existing coordinator's target policy/content renderer for real Fluxer-bound forum copies after source/recipient claims are operational.
- `fluxer-connector/src/service.ts`: use the existing `RPC_WRITES` operation set from `transport.ts`. At the SDK-owning boundary, compare fresh `session.health().bot_id` (authenticated login proof) with the **current** `currentClient?.user` (`bot === true`, nonempty matching `id`); if session otherwise reports `ready` but the identity comparison fails, the authenticated `health` result must instead report `state=degraded` while retaining the cached proof for diagnostics. Immediately before every effectful `config.execute`, take the current session health and live SDK identity, reject a `gateway_gap`, `gatewayFault`, or identity mismatch with `PrivateRpcError('unavailable', 503)`, and do not `await` between this admission check and delegation. This closes both Python health→RPC and cached-login→live-SDK identity gaps without a new session state machine; read-only methods may remain available. An SDK await already admitted before disconnect/identity change cannot be retroactively cancelled and follows S13 transport uncertainty; only a coordinator-managed caller owns a persisted retry fence.
- `permissions.ts`: distinguish forum post (`SEND_MESSAGES` and forum kind) from thread message (`SEND_MESSAGES_IN_THREADS`, server bit 38 via the pinned SDK's `permissionsIn(...).has(bigint)` path). Bot-owned mutations require fresh view/history eligibility, with ownership enforced against the exact fetched Message at both Python and Node boundaries; do not claim generic authority to edit/delete others' messages.
- `capabilities.ts`: stop returning unconditional false **only for measured and implemented features**, using fresh channel state, tag requirements and available operations. `FluxerAdapter._preflight()` must agree with this capability/ACL model. Continue to reject webhook mode, unsupported attachments and message-root thread creation. Any unverified provider shape remains false/`unsupported`, not an implementation guess.
- For a POST that might have reached Fluxer, preserve `unknown_delivery` and do not automatically retry within the direct RPC/adapter invocation; persistent no-replay across restart applies only to coordinator-managed claims (S13). The SDK `ForumChannel.threads.createPost()` hides its starter response; the existing `forum_create.ts` uses the SDK's vetted `rest.post(Routes.channelThreads(...))` shape and validates the server's embedded starter. Retain this single isolated exception, verified against the pinned SDK/server, rather than changing core receipt contracts.

### A4. Gateway observation and deferred publication

- Keep `FluxerInboundHandler` as authenticated, connector-scoped, **observation-only** ingress in #12; it is not a partial Fluxer→ActivityPub publishing adapter. Its current `MULTIPLATFORM_FLUXER_COMMUNITY_BINDING_PENDING` marker remains until #13 can prove community claim and verified Fluxer author. Do not route Fluxer DTOs into the Discord event router or bypass author validation with an instance-level bot identity.
- Use the existing SDK Gateway reconnect handling and verified parent/context enrichment. Failed parent lookup or contradictory guild is *unverified*, not an inferred forum membership; use persisted copy identity only for the existing exact ID-only mutation claim path.

### A5. Deployment and external evidence

- Keep Node-only token file, private bearer, network namespace and Compose health topology; adapt `.env` and operator runbook to an exclusive `BRIDGE_PLATFORM`. Verify Compose both with default profile (Discord) and with `--profile fluxer` using a Fluxer-only env. Ensure missing sidecar does not terminate HTTP/SQLite but leaves pending physical work offline.
- Run live acceptance **before** advertising production writes. If the physical tests fail, keep current production write handlers disabled, report #12 incomplete, and fix the measured contract; never claim acceptance based on mock-only tests or assume a server version from a fixture.

## Implementation Steps
