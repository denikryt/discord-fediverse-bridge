## Problem / Goal

CP35 passes the exercised Person Feed round trips, cross-guild mirrors, Undo and SQLite v2 checks. The pilot is nevertheless **FAIL**: NodeBB Community comment deletion and Group-wrapped root mutations do not change existing Discord copies; edits of a Discord Community source starter do not publish the intended Update; a title-less Personal Feed root acquires `Untitled Discord Post` on Update. The reviewer also requested nonduplicated webhook-root attribution, consistent Person handle input, readable Follow notifications and link-preserving Discord truncation. Separate NodeBB receiver defects, old sandbox behavior and unrepeated pilot cases must not be misreported as bridge fixes.

## Expected Behavior

An authorized change to a mapped Community post/reply reaches its Discord copies and, for a locally authored Community topic, the same canonical ActivityPub object. Title-less Person Notes stay title-less. Person commands address the same saved Follow by handle or Actor URL; webhook roots use webhook identity and keep a precise source footer; bridge-owned comments keep their reconciliation marker. A fitting link is retained rather than discarded merely because it crosses the original 2000-unit cutoff. Denied and ambiguous mutations have no unauthorized side effects. A focused pilot reports separately product defects, peer limitations, old suite failures and unexecuted tests. **Scope boundary:** keep the current source `MESSAGE_DELETE` behavior unchanged; do not add `THREAD_DELETE` handling, Group-signed outgoing moderation, a new author-delete command, or new rules for which Actor signs outgoing Delete. The known Discord topic/thread deletion failure remains deferred. Incoming authenticated direct/Group Community mutations (R01–R02) are separate and remain in scope.

## Specification

1. **R01 — Remote Community Delete routing.** An authenticated direct `Delete` for an already mapped NodeBB `/post/{pid}` chooses root vs comment using the **exact retained `(community_actor_id, object_id)` mapping**, not the URL path or an unscoped global lookup. A known comment produces a `comment.deleted` receipt and marks every eligible bot-created comment copy deleted, leaving the original Person/Community identity intact. A different Group, absent mapping, conflicting root+comment mapping or unauthenticated actor produces no deletion. An original wire delivery ID retains its idempotency scope; repeated deliveries cause no second side effect.
2. **R02 — Group-distributed NodeBB mutations and durable Group view.** An authenticated `Announce(Update(...))`/`Announce(Delete(...))` from an accepted, enabled, subscribed NodeBB Group G may change **only G’s Discord-distributed representation** of a known Person Note N. Match the verified outer signer, original `(G, canonical object ID, root/comment kind)`, immutable original owner and reply ancestry; inner `actor`, `attributedTo`, ID, type, audience and parent must be compatible with the verified first Create. G never becomes the Person signer, changes the Person canonical object, or gains authority over the same N in another Group. Direct author-signed mutations retain their existing authorization **and advance that Group view when they change an admitted mapped object**; a direct Delete also fences new placements. A later owner Update does not resurrect a Group-deleted distribution. Persist for each `(G,N,kind)` a current **Group-view projection**: canonical presentation payload, local monotonic revision and live/deleted state, separate from immutable `inbound_create_snapshot_json`. Preserve the applied Group-view revision and retry state for each attempted Discord destination, including ambiguous Creates before an ID is known. A valid Group Update advances the view; Group Delete records a terminal tombstone for this distribution and removes retained copies, even if `GET N` still returns 200. A replayed Create cannot clear that tombstone or use an obsolete first-Create payload for a new destination; after Update it uses the latest committed Group-view payload. A retry of an earlier Update (including one with partial Discord failure), after another Update or Delete, never rolls back a later committed revision. Existing deliveries with retained Discord IDs and ambiguous Create attempts whose exact Discord IDs can be proven through history converge on the current view after restart; inaccessible/inconclusive history remains durably **unresolved**, not falsely labelled converged or retried as a new POST. A request in flight across Update/Delete that later yields a proven ID is adopted and compensated; zero proof is never interpreted as absence of a POST. Store per-target applied revision, claim correlation format and delivery/retry outcome durably. Newly bridge-created remote Community roots place the complete canonical object ID on the **last line**; bot comments place exactly one full `[↗](<canonical_object_id>)` marker in the **fixed first author paragraph**. Exact expected forum/thread, bot identity, full marker and a **single** match are required to adopt an ambiguous result; content or URL substrings are not proof. Existing pre-v3 ambiguous claims without these markers remain unresolved until explicitly investigated. Exactly one accepted Group-announced activity maps atomically to one Group-view revision; a direct-owner activity may atomically advance each affected admitted Group view under one global receipt. For R02 events, commit a terminal receipt **in the same transaction** as every affected view revision (no earlier `in_progress` preclaim). Save a fingerprint of each validated normalized activity, including verified signer/Group, canonical object identity/kind, owner/parent, mutation content/audience and meaningful time fields. An identical event-ID replay returns its original receipt/revision without advancing; same ID with changed content/identity fails as a conflict even after later mutations. A crash before that transaction leaves neither new view revision nor blocking receipt; a crash after it leaves both. A denied signer, changed owner/parent, absent first-Create proof, disabled subscription or different Group causes **no view change and no Discord mutation**. A processed ingress receipt means the projection was committed, **not** that external Discord delivery succeeded; missing/failed copies remain visibly pending for independent retry. For distinct Update activities without a trusted sender sequence, local commit order defines display order; an explicit valid source timestamp may reject older events but is not silently treated as a verified global sequence. A Group Delete is terminal until a future separately specified, authenticated re-share generation (not part of this stage).
3. **R03 — Discord Community starter edit.** Editing the **source** forum thread’s original starter (already mapped to a registered user’s published Community root) updates the body of that existing AP publication and bot-owned mirror starters, while preserving saved title, Actor, AP object ID, recipients and reply ancestry. A raw edit explicitly containing `content: ""` means the user cleared the body and **must** produce a valid empty-body Update; an event without usable `content` triggers existing fetch/reconciliation rather than an empty Update. No second Note/Page is created. Mirrors, inbound/unmapped starters, an unrelated owner or a denied guild cannot reserve a user-authored Update.
4. **R05 — Title-less Person Update.** For `publicationContext in {'personal_feed','remote_person_feed'}`, root `Create(Note)`, public GET/outbox Note and subsequent `Update(Note)` omit `name` when no explicit title exists. Editing content changes only the intended mutable fields and advances the saved revision without altering Note/Activity ID, `attributedTo`, `inReplyTo`, `to`/`cc` or mirrors. Existing Community `Page` title defaults and titled Community posts retain their established representation.
5. **R06 — Remote webhook root attribution.** A bridge-created remote Person **webhook root** has no textual author-header line: webhook username/avatar already display the author. The final nonempty line remains the **full canonical `object_id`**, and Create/Edit/repeated Edit preserve it byte-for-byte under the Discord content budget. It is still matched only by the correct channel, webhook ID and full last line; arbitrary text resembling an ID does not reconcile. Bot-authored Remote/Personal comments and mirrors keep the existing author label and exactly one `[↗](<object_id>)` in the first paragraph. Original user-authored Discord content is not rewritten.
6. **R07 — Person command identity.** `/person-feed follow`, `add-channel`, `remove-channel`, `unfollow` accept a canonical HTTPS Actor URL or resolvable `@name@host` / `name@host` handle and act on the **same canonical remote Person identity**. Reuse the verified Fedify Person resolver and current federation policy; never use raw handles as database identity. Exact stored Actor URL supports local removal/Undo even when the remote server is offline; an unresolved handle fails without changing assignments or Follow. Authorization remains user/guild/channel scoped and is rechecked by the existing `BEGIN IMMEDIATE` write boundaries. Follow generation, Activity ID, one-channel-per-Follow-per-guild, other owners and cross-guild assignments are unchanged. **Retain `/person-feed add-channel`** until its removal is separately approved; no new command aliases or migration.
7. **R08 — Follow notification name.** For an incoming remote Follow of a local User Actor, resolve the **same remote Person**'s optional `preferredUsername`, then Actor `name`, otherwise the verified Actor URI segment. Render one bounded `@username@domain`-style label in the owner DM, avoiding duplicate domains and unsafe Markdown/mentions. Unavailable or mismatched profiles fall back without blocking durable Follow, signed Accept or existing at-most-once DM attempt; profile data never changes remote actor identity or delivery endpoint. A UID-based NodeBB Actor with `preferredUsername=nachitima` displays `@nachitima@space.nachitima.com`, not `@2@space.nachitima.com`.
8. **R09 — Link-preserving feed layout.** Reserve the exact root footer / comment marker and separators first, using **UTF-16 code units** and Discord's 2000-unit message budget. If full content fits, emit it unchanged. When it does not, prefer a **whole fitting URL/link** over adjacent expendable plain-text body: make a deterministic middle omission with `…` to free room before a crossing `http(s)` URL, `<http(s)://…>`, `[label with spaces](URL)` or `[label](<URL>)`. Preserve the order and spelling of retained content, balanced/escaped Markdown delimiters, media URLs and CW text; no truncated `https://`, `](` or reconciliation identity may be emitted. Reuse this layout for root/comment Create and Edit. If a full link cannot fit even after omitting all optional body text, the bridge may omit that link and indicate omission; the full source remains accessible via the mandatory root footer / comment marker. This physical-limit case is **not** a promise to preserve every arbitrarily long link. No extra Discord messages, embeds or URL-shortening service are introduced solely to evade 2000 units.
9. **R10 — Observable status and regression gate.** Record for each operation whether the authenticated event reached canonical lookup, policy, durable mutation, individual Discord/API deliveries and external recipient state. Do not treat HTTP 2xx, a `processed` receipt or a queued worker as external delivery. Compare against CP35 **per failing test ID**, with the reported baseline of Python 1217 passed / 215 failed / 6 errors / 1 xfailed, DiscordOps 50 passed, Gateway 53 passed / 6 failed; neither change assertions to hide failures nor relabel them as successes. Fix test fixtures only when they conflict with a proven current contract. Distinguish in-scope new regressions from shared historical and environment failures.
10. **R11 — Verification boundaries and peer limitations.** Repeat real L05/L06/L07/L09 and CP20 F04/F08/F10/F12/F25/F26 after deployment, including signed NodeBB Community Update/Delete, local starter edit, Personal-root Update, handle commands, notification and protected links. Repeat the previously *NOT VERIFIED* queue, uncertain-history, Follow-generation and concurrent assignment cases as separately gated experiments. A NodeBB 4.16.7 cached-parent `toPid` bug, an upstream `[label]()` link already broken before bridge ingress, and sandbox 0.2.1's timezone/unknown object routes are **peer-side** observations: provide reproducible upstream evidence/issue and retest after peer repair; do not add bridge-side forged parent IDs, legacy timestamp parsing or arbitrary foreign object lookup. Missing Mastodon, Lemmy or second Person T remain NOT VERIFIED until real peers exist.

## Architecture

### A. Trusted Group mutation boundary and persistent projection (R01–R02)

The ingress chain remains `fedify-gateway/src/federation.ts` → `normalize.ts` → `src/http_api.py` receipt → `src/activitypub_handlers.py` → `src/community_sync/runtime.py`. First reproduce captured NodeBB `/post/79` with exact `(Group, ID, root/comment)` evidence; never add a global object-URL fallback (R01). For R02, use the **Fedify-verified outer Group signer** and original `source_announce_id`; only a currently accepted NodeBB Group Follow may authorize a Group-view mutation. Keep `inbound_mutation_denial()` as the direct Person-signed path, but apply its accepted mapped edits/deletes to the same Group-view revision so direct owner updates do not leave new targets on the first-Create body. The separately authorized Group path checks first Create author, object identity, expected root/parent, inner activity type and payload before any durable view write or Discord I/O. An outer Announce signature does not authenticate the nested Person as its author.

**Durable data model and owner.** `CommunityThreadGroup` and `CommunityMessageGroup` **already own** the unique inbound `(community_actor_id, ap_object_id, kind)` mapping and immutable `(owner, root, parent)` evidence. Add `view_revision` (starts at 0 for admitted inbound rows), `view_state` (`live`/`deleted`), `display_object_json` (allowlisted current presentation; required for a live admitted view), optional verified `view_updated_at` and `last_view_activity_id` **to each existing typed canonical row**. The first verified `inbound_create_snapshot_json` remains immutable. Only verified remote inbound rows use these fields; local-source rows have no Group-view lifecycle. Different Groups distributing the same Note own independent projections and tombstones; no separate `CommunityGroupView` identity is created.

`CommunityDiscordTargetClaim` already owns the **same typed `(root-or-comment Group, channel)`** at the pre-POST, `unknown` and `completed` boundaries. Extend that existing claim with nullable `reserved_view_revision` (the revision rendered before Create POST), `reconciliation_marker_version` (NULL for pre-v3 attempts), `applied_revision` (last *proven* rendered/mutated revision), `mutation_attempt_token` (CAS for Edit/Delete), **one** `next_attempt_at` (history-check due time while `unknown`; mutation retry/lease deadline while `completed`) and bounded `last_error`. Preserve distinct Create `attempt_id`/`attempt_started_at` across all mutation attempts; late original Create responses must still be adoptable. `status` selects scheduling: `claimed/unknown` is pre-ID uncertainty, `completed` has a typed delivery and can run latest-view Edit/Delete, `failed` only permits existing proven pre-send retry. A claim with `applied_revision < canonical.view_revision` is due when no current mutation token or when its lease/due time has expired. A timed-out Edit/Delete remains an idempotent retry of the **current** revision; never replay the old event body. The scheduler uses claim CAS and bounded scans, not a second per-delivery cursor or a second error store. An absent Discord ID cannot be inferred from a claim status; `CommunityThreadGroupDelivery`/`CommunityMessageGroupDelivery` remain the sole proven Discord ID/ownership records. `finish_remote_target()` commits the proven delivery, `status='completed'` and `applied_revision=reserved_view_revision` in one writer transaction; if a newer Group revision committed during POST, that claim is still due.

Add nullable `mutation_fingerprint` (hex SHA-256 of trusted canonical mutation fields) and optional `group_view_revision` to `ActivityPubEventReceipt`; **do not add `group_view_id`**. For a single-Group Announce the verified Group/object/kind already identifies the canonical row, so its original revision may be recorded on the receipt. A direct-owner activity affecting multiple Group rows atomically advances all of them with one global fingerprinted terminal receipt; `group_view_revision` is NULL rather than pretending there was one common Group revision. Each canonical row and claim owns its own revision, while the global receipt fences replay of the original author event. There is no new AP object, subscription lifecycle, Group owner, view table or view-delivery table.

**Crash-safe R02 receipt admission.** At `src/http_api.py::receive_activitypub_event()`, route only a **verified, recognized R02 Group mutation or direct-owner mutation affecting mapped Group views** to a narrow transactional repository operation instead of the legacy `_begin_event_attempt() → dispatch → _finish_event_processing()` lifecycle. Verify Gateway bearer and signed-envelope claims first; resolve any required remote JSON outside the DB transaction, never treating the fetched Person Note as proof of Group distribution. Within **one `BEGIN IMMEDIATE`**, compute SHA-256 over deterministically serialized UTF-8 JSON (sorted keys, stable separators) containing verified Group/outer actor, activity ID/type, canonical object ID/kind, immutable owner/parent, normalized (sorted, deduplicated) `to`/`cc`, changed content and authenticated update instant. First compare the digest with an existing receipt for that verified wire ID: return the original terminal result without side effects even if the subscription has since been cancelled; reject a mismatch. For a **new** activity, recheck current Group binding, first-Create provenance, owner/parent/kind and signer before writing. Use only semantically relevant normalized fields; transient transport headers/receipt timestamps must not affect the digest. Query/insert the **terminal `processed` receipt**, `mutation_fingerprint`, associated view revision and view payload/tombstone **in that same transaction**, without an earlier `in_progress` write. Identical replay compares fingerprint and returns the stored terminal response; different digest under the same delivery-ID scope returns HTTP 409 without touching the view, even after later U2/D. Global direct-owner receipt may cover multiple admitted Group views atomically. Before-commit crash leaves neither new receipt nor new revision; after-commit crash replays the already committed result. The old receipt lifecycle remains unchanged for Create, Follow and unrelated events. Receipt `processed` means persisted Group-view transition, **not** successful Discord I/O. Legacy pre-v3 receipts without fingerprint are not silently reclassified as validated R02 events; audit and explicitly reconcile any old blocking `in_progress` rows before rollout.

**Admission and delivery.** For the R02 writer transaction above, validate policy and immutable identity before incrementing revisions. `Delete` makes the view terminal regardless of whether the original Note remains fetchable (GET 200). Distinct Updates accepted before Delete advance the view, not the first Create; a previously accepted event ID never advances it again. When source timestamps are present and authenticated, enforce monotonicity; when absent, record the **local acceptance order**, without pretending to recover sender chronology. An explicit new Group re-share after a tombstone is outside this stage and must not be emulated by replaying Create.

`DiscordFanoutGroupRepository.reserve_remote_target()` must check the **typed canonical Group row’s `view_state`** **inside its existing serialized target-admission transaction**; for live view it returns a stable snapshot of `display_object_json` *and* `view_revision` and persists `reserved_view_revision`/marker version on that same claim before REST. It does not use `GET Person Note` as evidence of current Group distribution. After `create_thread`/comment POST, `finish_remote_target()` commits the typed Discord delivery and claim `applied_revision` for the sent revision; if the canonical row advanced during REST, the **same completed claim** remains due for correction. Never interpret a new target `reserved_view_revision` as permission to POST if the view is now `deleted` before the request begins.

**Ambiguous Create reconciliation.** Reserve and store the claim's marker version and rendered view revision **before** the REST call. Only new bridge-owned *remote Community* roots and comments use this layout: for a root the formatter reserves the **complete canonical `object_id` as final line**, with the original source `url` optionally retained earlier; for a comment reserve exactly one `[↗](<object_id>)` in the first backtick-escaped author paragraph. Compute Discord's 2000-unit budget after preserving this mandatory identity; invalid/oversized ID is a **pre-REST failure**, never a truncated marker. Create and subsequent Edit use the same identity structure, including full canonical URL validation against control characters and unsafe Markdown destinations; existing Discord-authored source messages are untouched. The existing Person-feed formatter/matcher remains separate. No marker is retroactively presumed for legacy `unknown`/`claimed` claims.

On timeout mark the **same claim** `unknown`. After a process crash, a `claimed` attempt older than **120 seconds** (`attempt_started_at`) moves by CAS to `unknown` for reconciliation (never for resend); this is a reconciliation-only transition, not proof of an unsent POST. Preserve its attempt token; a late original success with that token may still be adopted if no conflicting delivery exists. A bounded, permission-checked history probe searches the claim's **expected forum** (root: accessible active/archived threads and bot-owned starters) or the **exact expected mapped Discord thread** (comment: bot-owned messages with the correct same-Group parent). Require the correct Group/channel, bot author ID, **exact** full final-line root ID or first-paragraph comment marker, and **exactly one** candidate. Do not infer success from title/body similarity, URLs elsewhere, `/42` vs `/420`, or an incomplete archived-thread scan. When proven, atomically adopt that original Discord ID as the typed delivery, mark the same claim `completed`, set `applied_revision=reserved_view_revision`, then let its revision gap schedule latest-view Edit/Delete. On unavailable/incomplete history, zero matches or multiple candidates, keep `unknown` as a visible **unresolved** outcome, persist a bounded `last_error` and advance the claim’s shared `next_attempt_at` no sooner than **5 minutes**; scan due claims with cursor pagination and a separate bounded network-attempt limit; never re-POST without independent proof of pre-send failure. A late HTTP success for the same attempt token may complete this adoption safely, even if the claim was moved to reconciliation-only status. Pre-v3 `unknown`/`claimed` claims, which lack guaranteed markers, are reported for manual review, not auto-adopted or retried.

A **completed claim** with `applied_revision < canonical.view_revision` is due for idempotent EDIT or DELETE **only on its retained bot-owned Discord ID**; the drain CAS-claims `mutation_attempt_token`, reads the newest committed canonical `display_object_json`/tombstone, and never uses an old event payload. After REST, the completion CAS updates `applied_revision` to only the attempted revision and clears the token; a newer concurrent Group revision stays due. `next_attempt_at` is the retry/lease deadline so an interrupted mutation token is reclaimable after restart without blocking that claim forever. A failed / timed-out Edit/Delete leaves a due claim and is retried with bounded backoff and fairness after restart. Treat already-deleted remote copies (proved 404) as deletion success; forbid edit of a deleted Group view. Recheck ownership and eligible subscription before an Update edit, allow scoped cleanup of already retained copies on Delete without creating new content. Crash/restart, concurrent Update/Delete, and a POST that crosses a Delete converge **for known-ID or uniquely proven adopted copies**. Ambiguous copies without conclusive Discord evidence remain unresolved and do not count as a successful delivery or clean deletion. Signal the existing ready-gated runtime worker; a minimal `src/community_sync/group_view_delivery.py` module may host the worker, but do not build a generalized event bus.

**SQLite contract.** This behavior needs **SQLite v3**, but **no new Group-view/cursor tables**. Keep unchanged `src/db/schema_versions/v1.sql` and `v2.sql`. Add columns to `community_thread_groups`, `community_message_groups` (`view_revision`, `view_state`, `display_object_json`, `view_updated_at`, `last_view_activity_id`), `community_discord_target_claims` (`reserved_view_revision`, `reconciliation_marker_version`, `applied_revision`, `mutation_attempt_token`, `next_attempt_at`, `last_error`) and `activitypub_event_receipts` (`group_view_revision`, `mutation_fingerprint`); declare appropriate state/revision CHECKs in **v3**. For original/local-source Group rows, leave Group-view fields NULL and never route them through inbound Group mutation admission. Initialize a verified remote first-Create snapshot to `live`, revision 0 and its canonical display object using the **saved immutable snapshot**, not a replay or GET of the author Person Note. If an old remote row lacks valid first-Create evidence, leave it **ineligible**, audit and do not fabricate view payload. Source mutations that were never durably recorded before v3 cannot be reconstructed from an immutable initial snapshot; audit known historical mutation receipts and report this limitation rather than silently claiming their state is current.

For pre-v3 **proven** bot-owned inbound deliveries (`role='inbound'`, matching remote typed Group and channel) with no target claim, backfill **one** `status='completed'` claim with `applied_revision=0` only after confirming its retained Discord ID/ownership; preserve the typed delivery row. Existing claims are never overwritten by this backfill. In particular, markerless `unknown`/`claimed` claims stay unresolved with their original token/status, and legacy `in_progress` receipts keep their existing identity until explicitly audited. Do not infer delivered from old receipt `processed`, create a claim for local-source or unrelated mirror deliveries, or reset historical errors. Keep exact DDL in new `v3.sql`, atomic `v2_to_v3.py`, version registration and `DATABASE_VERSION=3`, plus schema guard, FK/integrity and strict migration tests for `v0→v1→v2→v3`, `v1→v2→v3` and `v2→v3`. Ensure older migration steps do **not** create or retrofit v3 fields through `Base.metadata`; use the explicit v2→v3 step. Before operating on a live dev DB obtain separate approval, backup and disposable-copy rehearsal; older CP35 code must reject v3 without modifying it.

**Precedents:** [ActivityPub §7/§7.11](https://www.w3.org/TR/activitypub/) separates owner Update/Delete from Announce distribution; the [W3C SocialCG authorization primer](https://www.w3.org/wiki/SocialCG/ActivityPub/Primer/Authentication_Authorization) explains object-authority verification. CP35’s unique typed Group rows and `reserve_remote_target()`/`finish_remote_target()` preserve the canonical and per-target owners; extending those rows avoids separate one-to-one view/cursor lifecycles. The simplification review’s six SQLite model probes validate that *representation* only, not the future worker or live history proof. The immutable first-Create snapshot remains provenance; `formatting.py::has_feed_comment_identity()` and `remote_person_webhooks.py::find_created_root()` demonstrate full-marker, sender-scoped proof instead of substring matching. Adapt that **only** to new inbound Community bot outputs; history ambiguity stays unresolved. [SQLite transaction atomicity](https://www.sqlite.org/lang_transaction.html) supports committing authenticated receipt identity and projection in one `BEGIN IMMEDIATE`, before network delivery. The project's exact DDL snapshot/atomic `run_pending_migrations()` and [SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html) are the v3 migration precedent. Never infer Group-view state from GET of the author-owned Note.

### D. Fediverse presentation and one renderer budget (R06, R08–R09)

Make `src/remote_person_webhooks.py::remote_root_content()` output only `body/CW/media + '\n\n' + full object_id` (or the footer alone for empty body). Extract a small common **mandatory-layout/budget composer** from `src/formatting.py` so webhook roots may have an empty author header while `feed_comment_content()` still requires a nonempty escaped actor label and exact first-paragraph marker. Keep `find_created_root()` full-last-line/webhook/channel verification and `has_feed_comment_identity()` strict. No text-header removal from bot comments or original Discord messages.

Replace the current “crossing link ⇒ omit link and entire tail” rule with a bounded, deterministic link-aware fit policy. Scan supported URL/Markdown atoms (including parentheses, escapes, Unicode and CW/media), budget immutable strings first, and preserve the earliest **whole links that can fit** by removing adjacent optional plain text and showing a middle `…` at the removed segment. Prioritize (1) mandatory identity, (2) earlier retained complete links in order, (3) maximum available surrounding text without exceeding 2000 UTF-16 units; if an atom exceeds the **entire optional body budget**, skip it as physically impossible and show `…`. Limit parsing to the supported forms, keep linear/bounded work for long adversarial text; do not write a global Markdown parser or reflow raw user-owned Discord text. Create and Edit call the exact same formatter. If all retained atoms still cannot fit, remove only optional body content. The existing canonical source link lets recipients access omitted content. Check both Discord API's actual saved `content` and rendered clickable URL, not CommonMark alone.

**Precedents:** [Discord Message API content limit](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx), [Discord Markdown](https://support.discord.com/hc/en-us/articles/210298617-Markdown-Text-101-Chat-Formatting-Bold-Italic-Underline), local `formatting.py::_feed_protected_spans()` and CP35's exact reconciliation markers. Read `preferredUsername` or Actor `name` *from that matching profile* into an optional bounded display field in `fedify-gateway/src/types.ts` and `src/activitypub_models.py::LocalFollowRequestEvent`; `src/user_actor_followers.py::_notify_owner()` uses the display field after the durable Accept. If profile lookup fails, keep the current URI-segment fallback. Do not persist the field as an identity, fetch other hosts solely for a label, or change the `owner_notification_state='attempted'` at-most-once semantics. Use existing `feed_author_header` sanitization principles without copying Community body layout into DMs.

### E. Canonical Person command lookup (R07)

Keep identity resolution at an async boundary shared by the four Person commands, not in `RemotePersonChannelService`'s SQLite transaction. For a string equal to an already owned canonical Actor URL, select that ID from the saved Follow without network; for a handle, call the **existing** `RemotePersonFollowService`/Gateway `resolve_remote_person()` (WebFinger/Fedify) after federation-policy precheck and verify that the returned canonical ID is an existing owned Follow for mutation-only commands. For a new `follow`, preserve current canonicalized resolution and generation rules. The write service receives only `remote_actor_id`; do not silently create a Follow while handling `add-channel`. Recheck ownership, policy, channel permission and group unique-index constraint at admission. Denied host, changed remote Actor ID, invalid URL, timeout or mismatched owner must leave current assignments/Undo state untouched; exact canonical-ID offline removal remains available.

**Precedents:** `RemotePersonFollowService.follow()` already separates remote discovery from `BEGIN IMMEDIATE`, and the v2 unique `(follow_id, discord_guild_id)` index serializes concurrent assignment. WebFinger discovery is an input transformation, never an ownership mechanism. `/person-feed add-channel` is retained by explicit scope decision; no temporary alias table or backwards-compatibility shim is introduced.

### F. Validation and external boundaries (R10–R11)

An upstream receiver may still fail until patched; no bridge “fix” should forge `toPid`. Preserve the **frozen v2 snapshot** and Plan 145 Follow/queue identity and suppression rules while targeting exact SQLite **v3** only through the approved migration; the separate roadmap items in `dev/future_tasks.md` (signing-key isolation and lost-channel restoration) are outside this stage.

**Temporary compatibility/fallback/migration mechanisms:** none are authorized by this plan. ## Open Questions / release blockers

1. **SQLite v3 deployment authorization.** Code and test the atomic migration on disposable copies first. Obtain separate approval/backup plan before upgrading the actual CP35 v2 dev DB. Read-only audit the live v2 DB for pre-v3 `unknown`/`claimed` Community claims and orphan `in_progress` Group-mutation receipts before upgrade; preserve every row and disclose a manual reconciliation plan, because older output lacks a reliable marker/fingerprint. Do not silently apply an experimental schema change during field checks. `v3` is required for the full R02 guarantee; retaining a no-DDL constraint would require intentionally dropping the late-target/retry guarantees and re-reviewing the specification.
2. **NodeBB outer signature and ordering.** Capture the real signed `Announce(Update/Delete)` and check exact signer, ID, `updated`, owner and ancestor fields. Without trustworthy outer signer, the mutation remains denied. Distinct Updates without an authentic remote sequence are ordered by local acceptance; do not promise reconstruction of missing peer chronology. A new Group re-share after a tombstone needs its own policy/epoch model and is not implemented here.
3. **History evidence availability.** A root created into a forum may later be archived or hidden; the root reconciliation scan must use available active/archived thread APIs with bounded pagination and access checks. A partial scan cannot establish absence; leave claim unresolved without a new POST. Verify the bot author ID and exact marker in real Discord before declaring history recovery PASS.
4. **Peer coverage.** NodeBB cached-parent and old sandbox implementation defects remain external. Mastodon/Lemmy/second remote Person T need a test environment; mark them NOT VERIFIED until executed.
