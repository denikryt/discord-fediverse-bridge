# Known issues and verified behavior

- Valid inbound activities from communities with no accepted bridge subscription are ACKed at the ActivityPub layer and skipped locally unless they relate to already mapped bridge context.
- Local community Undo(Follow) removes the remote-subscriber row and future local-community fanout uses current accepted remote subscribers as the delivery source of truth.
- `/subscribe-channel` can discover same-instance bridge-owned local communities and persist local subscriber rows. Stage 5 makes active local subscriber forums source-capable for new posts/comments and authoritative for edits/deletes of their own canonical surfaces.
- Stage 1 compatibility cleanup on 2026-05-27 removed the old Python alias/wrapper vocabulary for remote ActivityPub subscribers and removed the gateway reader alias/fallback for that naming layer. Deployed-database upgrade support still remains in `Database.migrate()`, so legacy schema compatibility continues to be owned by Stage 0's explicit `migrate existing DB` decision rather than by runtime naming aliases.
- Local subscriber fanout uses missing surface rows as the create retry signal; edit/delete retries are currently reprocess-based and do not use a dedicated per-surface mutation receipt table.
- Stage 0 compatibility-cleanup inventory on 2026-05-27 verified that the deployment database is `sqlite:///./bridge.db`. Backup was captured at `notes/db_backups/bridge-stage0-2026-05-27.sqlite3`, the legacy `local_community_followers` table was absent, and `local_community_threads` / `local_community_messages` no longer expose the old canonical Discord id columns. Cleanup stages should therefore proceed from the explicit decision `migrate existing DB`, not `discard old DB`.
- The same Stage 0 run verified that the live database still needed the additive Stage 3 surface migration for `local_subscriber_id` on `local_community_thread_surfaces` and `local_community_message_surfaces`. Running `Database.create_all()` plus `Database.migrate()` through the project `.venv` applied that migration successfully; the system `python3` environment is not suitable for bridge operations because it lacks the Pydantic v2 API required by `src/config.py`.
